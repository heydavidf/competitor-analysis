# AGENTS.md

Guide for coding agents changing this repository. To use the skill rather than change it, follow the [README](README.md).

## What this is

One Agent Skill, `competitor-analysis`. It tells an agent how to compare the alternatives a customer could use for one important task and produce three files: `research-matrix.csv`, `competitive-analysis-brief.md` and `dashboard.html`. It is Markdown plus one HTML template; the only code is a small example generator, the layout check, the tripwire script and their tests (Python standard library and Bash).

## File map

| Path | What it is |
|---|---|
| `skills/competitor-analysis/SKILL.md` | The skill's entry point and the source of truth for its behaviour |
| `skills/competitor-analysis/references/method.md` | The working method the skill reads before research |
| `skills/competitor-analysis/templates/dashboard.template.html` | Dashboard template with one `__DASHBOARD_DATA__` token |
| `skills/competitor-analysis/LICENSE` | Copy of the root `LICENSE`, so installed copies carry it |
| `examples/fictional-food-swap/` | Wholly fictional worked example. `example-data.json` and `fixtures/` are the editable inputs; `research-matrix.csv` and `dashboard.html` are generated by `build_example.py` |
| `tests/` | Unit tests for the layout check and the tripwire (standard library `unittest`) |
| `.github/check_skill_layout.py` | Checks the `skills/<name>/` layout that `gh skill install` needs |
| `.github/tripwire.sh` | Catches personal paths, junk files and silenced checks |
| `.github/workflows/ci.yml` | Runs every check below on GitHub |

Everything the skill needs at runtime lives inside `skills/competitor-analysis/`. An installed copy contains only that folder, so links in the skill's Markdown must stay inside it. Repository files (README, LICENSE, CHANGELOG, examples, tests, `.github/`) stay at the root.

## Checks

Run these from the repository root before saying a change is done, and quote their output. CI runs them too, plus the extra checks below.

```sh
pipx run --spec ruff==0.17.1 ruff check --no-cache .
pipx run --spec ruff==0.17.1 ruff format --no-cache --check .
python3 -B -m unittest discover -s tests -v
python3 -B .github/check_skill_layout.py
python3 -B examples/fictional-food-swap/build_example.py
git diff --exit-code -- examples/
bash .github/tripwire.sh origin/main
```

The tripwire compares committed changes with the base you give it, so commit first. If your clone has no `origin/main`, pass the commit your branch started from instead; the tripwire fails if it cannot make the comparison.

Also validate the skill format with [skills-ref](https://github.com/agentskills/agentskills) (CI pins commit `69ef37e9424c0a7ea9dd2293b559e43ec8176379`) in a temporary virtual environment outside the repository, then run `skills-ref validate skills/competitor-analysis`. CI also checks that `gh skill` can discover the skill (`gh skill publish --dry-run` on an exported copy of the tree), installs it with `gh skill install --from-local . competitor-analysis --dir <temporary folder>`, scans for secrets with gitleaks and checks links with lychee.

The example generator rewrites `research-matrix.csv` and `dashboard.html` from `example-data.json` and the template. If you change the template or the example data, run it and commit the regenerated files; the `git diff` step fails when they are out of date.

## Working rules

1. A bug fix ships with a committed test that fails on the old code and passes on the new. A one-off check in a temporary folder does not count.
2. Run every check listed above before saying done, and quote the output.
3. Do not silence a check to get green (for example a `noqa` comment or a skipped test). The tripwire fails the build unless the line says `tripwire-allow` with a reason.
4. Stop any server you started. Leave no stray files (caches, scratch files, generated study output) in the repository folder.
5. For non-trivial changes, a different agent writes an independent scenario test before the change is accepted.

## Releasing (maintainer only)

`gh skill install` without a version installs the latest GitHub release, so fixes reach users only after a new release. Put a CHANGELOG entry with the new version in the pull request. After it is merged to `main` and CI is green, run `gh skill publish --tag vX.Y.Z` from a clean clone of `main`. It validates the skill and creates the tag and release. Agents never publish without the maintainer's explicit approval.

## Constraints

- The example must stay fictional. Never add real customer data, confidential research or copied third-party text.
- Keep the skill's folder name and its `name` in `SKILL.md` identical.
- The skill's own writing rules apply to its instructions and outputs, including no em dashes.
- Changes to the method or behaviour in `skills/competitor-analysis/` need a CHANGELOG entry that says what changed for users.
